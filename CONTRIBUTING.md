# Правила работы над проектом «Трекер реабилитации пациентов»

## 1. Соглашение по именованию веток в Git
Мы используем следующие префиксы для веток:
* `main` — стабильная ветка (в неё попадает только проверенный и рабочий код).
* `develop` — основная ветка для текущей разработки.
* `feature/название-задачи` — для новой функциональности (пример: `feature/add-auth`, `feature/exercise-tracker`).
* `bugfix/название-ошибки` — для исправления ошибок (пример: `bugfix/fix-header`).
* `docs/название-раздела` — для обновления документации (пример: `docs/update-readme`).

## 2. Правила написания кода и комментариев
* **Стандарт:** Мы используем **PEP 8** (официальный стандарт оформления кода Python).
* **Именование:** `snake_case` для переменных и функций (например, `calculate_progress`), `PascalCase` для классов (например, `PatientProfile`).
* **Комментарии:** Код должен быть самодокументируемым (понятные имена переменных). Сложные участки логики обязательно комментируются. Каждая функция и класс должны иметь строку документации (docstring).
* **Форматирование:** Для автоматической проверки используются линтеры `flake8`, `black`, `isort`.

## 3. Процедура Code Review (проверки кода)
1. Разработчик создает новую ветку от `develop` (например, `feature/add-login`).
2. Вносит изменения, делает коммиты и отправляет ветку на GitHub.
3. Разработчик создает **Pull Request (PR)** в ветку `develop`.
4. В описании PR указывается: что было сделано и как это проверить.
5. **Проверяющий:** Второй участник команды (тимлид или напарник) проверяет код. Код не может быть слит (merge) в `develop`, пока проверяющий не поставит Approve (одобрение) и не пройдут автотесты.
